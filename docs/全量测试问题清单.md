### 1. C2 枚举值误报
```
现象：ADD APN:..., VIRTUALAPN=DISABLE  → 判「DISABLE 悬空」
原因：VIRTUALAPN 以 APN 结尾，被 REF_PARAM_SUFFIX 命中当引用
     但值是枚举开关，不是对象名
修法：加 ENUM_VALUE_BLACKLIST（ENABLE/DISABLE/TRUE/FALSE/INHERIT...）
判别力：5/5 通过（含 3 个反向验证）
影响工单：NC20260803002122
```

### 2. G18 同族多动词变体误报
```
现象：意图写「APN 配置」→ G18 报「缺 MOD APN、RMV APN」
原因：INTENT_FAMILY_MAP['APN'] = ['ADD APN','MOD APN','RMV APN']
     要求三个动词全部出现
修法：同族变体按族名分组，命中任一即满足
判别力：4/4 通过
影响工单：NC20260911000610 / NC20260828001294 /
         NC20260921001905 / NC20260806001514 / + 4 个轮询超时
```

### 3. emit 跨作用域 NameError
```
现象：NameError: name 'emit' is not defined
原因：emit 是 call_hermes 内部闭包，run_agent 里访问不到
修法：直接用 events_fp 写事件
影响：只在 rescue_tmp_artifacts 真捞到草稿时触发
```

### 5. 死循环误杀（4 个工单）
```
现象：「检测到 Code↔Guard 连续交替 4 次，判定为死循环」
      或「guard_check 被调用 11 次（上限 10）」

问题：只看交替次数，不看错误内容
     · 如果每次 Guard 报同一个错 → 真死循环（该杀）
     · 如果报不同的错 → 在逐步收敛（不该杀）

修法：
  · 记录每次 guard_check 的 fatal 内容哈希
  · 只有「连续交替 且 fatal 完全相同」才判死循环
  · MAX_GUARD_CALLS 10 → 15（给多条 fatal 逐步修留余量）

影响工单：NC20260811002706 / NC20260911000486 /
         NC20260911000610 / NC20260921001905
```

### 6. 轮次上限 900s 太短（3 个工单）
```
现象：「第1轮耗时 912-1560s 超过 900s 上限」

问题：复杂工单正常就需要 10-25 分钟

修法：按复杂度动态调整（见第 7 项）
  · 简单（params.csv < 100 行）：900s
  · 中等（100-500 行）：1200s
  · 复杂（> 500 行）：1800s

影响工单：NC20260806001780 / NC20260825001638 / NC20260828000360
```

### 7. 调度分档指标错误
```
现状：按 EXP 大小分档（≥30MB 串行 / 15-30MB 2路 / <15MB 3路）

问题：实测 EXP 大小与真实复杂度相关性只有 0.23（几乎无关）
     而 params.csv 行数相关性达 0.98（几乎完美）

证据：
  0-10 条 GT    → EXP 中位 1.9MB
  301+ 条 GT    → EXP 中位 16.1MB
  两者 EXP 只差 8 倍，但命令数差 100 倍

修法：改用 params.csv 行数分档
  · < 100 行：4 路并行，900s 上限
  · 100-500 行：2-3 路并行，1200s 上限
  · > 500 行：串行，1800s 上限

好处：复杂工单串行避免互相拖累，简单工单高并发提速
```

### 8. 脚本轮询超时 1800s 与 agent 上限不匹配
```
现象：4 个 timeout（0s / 0 条命令），但 agent 仍在跑

原因：脚本 deadline = 1800s
     但修复第 6 项后 agent 上限可能到 1800s
     → 脚本会先超时

修法：脚本 deadline 改成「agent 上限 + 600s 缓冲」
     或直接去掉脚本超时，靠 agent 自身的上限兜底
```
