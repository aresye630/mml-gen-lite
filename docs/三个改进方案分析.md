# 三个改进方案分析（数据支撑）

## 方案 1：MOD/ADD 视为等价

### 用户判断
> MOD 目标能达成和 ADD 一样，就不能算错。很多 MOD 限制很多，
> 所以用户一般自己写的时候就用 ADD。CSV 输入时和 EXP 对不上，就只能用 ADD。

### 实测收益
```
严格口径（动词必须对）: 族完备 43.3%
ADD/MOD 视为等价:      族完备 49.1%
提升:                  +5.8pp
```

### 结论
✅ 值得做。改评估判据即可，零风险。

但要注意：RMV 不能和 ADD/MOD 等价（删除和新增是相反操作）。

### 具体设计
```
等价组：
  {ADD, MOD}  → 视为同一族命中
  {SET}       → 与 {MOD} 部分等价？需确认
  {RMV}       → 独立，不等价

用户补充说法：「SET 系列和 MOD 类似，都是改属性」
→ 建议等价组：{ADD, MOD, SET} vs {RMV}
```

## 方案 2：SET 系列的命令链发现

### 用户判断
> SET 这个系列 EXP 中应该有对应的命令链的，这个查一下。

### 实测结果（38MB EXP，25 万条命令）
```
ADD APN: 615 条
SET APNxxx: 31 个族，每个 615 条，ratio = 1.00

  SET APNUEMUTACC     615
  SET APNL2TPATTR     615
  SET APNAFFUNC       615
  SET APNTETHERFUNC   615
  SET APNSRVSTATFUNC  615
  SET APNHTTP2DGRD    615
  SET APNSGLPASS      615
  SET APNTETHERDETSW  615
  ... 共 31 个
```

### 判据：现有 exp_siblings 找不到它们
```
exp_siblings(ADD APN) 返回 4 个：
  POOLGRPMAP / TCPMSS / ACLBINDAPN / VPNINST
  ← 都是「参数名指向 APN」的族

SET APNxxx 没有指向 APN 的参数名（它自己就是 APN 的属性命令）
→ 「参数名指向」判据看不见
```

### 新判据：同名前缀 + 数量 1:1
```
判据：SET <X>xxx 的族名前缀 == ADD <X> 的族名
     且 数量比值 >= 0.9
     
实测：ADD APN → 31 个 SET APNxxx 全部 ratio=1.00 ✅
```

### 收益估算
```
GT 里 SET/MOD 类命令 2935/12802 = 22.9%
产物里只有 619/3360 = 18.4%

三个大工单缺 35-51 族，全是 APN 属性类：
  NC20260811002706  缺 51 族
  NC20260806001780  缺 35 族
  NC20260828000360  缺 41 族

如果补上这些，族完备可能提升 10-20pp
```

### 结论
✅ 值得做。扩展 exp_siblings 加「同名前缀」判据。

## 方案 3：外挂知识库 / 后置 skill 修正

### 用户判断
> 这些改动本身是不是可以使用外挂知识库，如果现有的能力就现在这个样子了；
> 可以在 agent 之后单独使用经验 skill 自行修正意图进行改进。

### 分析：三种实现路径

#### 路径 A：外挂知识库（前置）
```
形态：YAML/JSON 规则文件，在 agent 生成前注入 prompt
内容：APN → 31 个属性命令的配套关系

优点：确定性高，零推理开销
缺点：需要人工维护，覆盖有限
风险：可能变成硬编码（红线）

结论：只能放「从 EXP 统计出来的通用规律」，不能放具体族名清单
```

#### 路径 B：后置 skill 修正（后置）
```
形态：agent 产出 mml 后，跑一个 skill 检查并补全
内容：读 EXP 找同类对象的完整配置链，补上缺失的属性命令

优点：不影响主流程，可独立迭代
缺点：需要二次 LLM 调用（成本）
关键：怎么知道「该补什么」？还是要靠 EXP 共现规律

结论：可行，但本质还是需要方案 2 的判据
```

#### 路径 C：意图二次修正
```
形态：agent 产出方案后，另一个 agent 读意图 + 产物 + EXP，
     判断「是否遗漏了命令族」，补充

优点：能发现语义层的遗漏（不只是统计规律）
缺点：成本高，可能过度补充
```

### 我的判断
```
方案 3 的前提是方案 2 已经做完了。
如果没有「SET 前缀配套」这个判据，
后置 skill 也不知道该补什么。

顺序应该是：
  1. 先做判据（方案 2）→ agent 生成时就知道要配 31 个属性命令
  2. 后置 skill 只做兜底（漏了的再补）
```

## 建议的实施顺序

```
第 1 步  方案 1（评估口径改等价组）      —— 立刻 +5.8pp，零风险

第 3 步  方案 3（后置 skill 兜底）      —— 方案 2 做完后再看是否需要
```
