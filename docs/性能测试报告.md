## 四、发现的问题

### 4.1 c4 耗时波动 9 倍（100s → 905s）

**现象**：同样输入，模型走了完全不同的探索路径。

```
第1次  100.6s  29 工具  41 API  pass
第2次  165.9s  41 工具  --       pass
第3次  905.4s  33 工具  --       卡在探索（无产物）
第4次  271.8s  --       --      Code↔Guard 循环
```

**根因**：LLM 推理不稳定，不是代码缺陷。

**已有的防护**：
- 工具调用 >300 次 → 杀
- guard 调用 >8 次 → 杀
- Code↔Guard 交替 ≥4 次 → 杀
- 单轮 >900s → 杀
- **新增**：>300s 且无产物 → 判卡住

### 4.2 测试中修的 4 个统计口径 bug

| bug | 影响 | 修复 |
|---|---|---|
| 工具计数按输出行算 | c1 报「301 次」误杀，实际 6 次 | 只数含 `┊` 的工具行 |
| API 按全日志统计 | 多用例累加（67→98→115→135）| 按 session_id 窗口过滤 |
| 多轮 run 共用 round1_out.txt | 前两轮被覆盖，无法统计 | 每次 run 独立 runN/ 目录 |
| 日志脱敏 `***` 干扰 | 误判为产物差异 | 确认真差异（agent 真漏了 DISABLE）|

### 4.3 G19 判定语义（已修正）

```
原来：@src=exp:L### 要求值必须出现在那一行
      新对象的价值必然不在现网 → 全部误报

现在：族匹配 + 行号真实 → 通过（参照格式）
      值也对得上 → 升级为强依据（复用对象）
      族不匹配 / 行号越界 → 仍然拦住
```

判别力测试：单行 + 区间 8 个场景全通过，2 个关键反例（FILTER 标到 HOST 行/区间）都被拦住。

## 五、性能规格建议

| 项 | 实测值 | 建议配置 |
|---|---|---|
| 单轮超时 | 100-270s 常态 | 900s（硬上限）|
| 无进展判定 | 300s 无产物 | 300s |
| 工具调用上限 | 29-80 次常态 | 300 次 |
| guard 调用上限 | 1-4 次常态 | 8 次 |
| 并发会话 | —— | 受 deepseek 限流，建议 ≤3 |
| 单会话内存 | —— | ~500MB（3 个 MCP 子进程）|

## 六、结论

**性能可接受**：
- 单次生成 100-270 秒，用户可等待
- 工具耗时占比低（5-25%），瓶颈在 LLM
- 缓存命中率 95%，重复查询成本低

**主要风险**：
- c4 那类「反复探索不落笔」的情况，靠防护机制兜底
- 需要更明确的 prompt 引导「先落草稿再精修」
