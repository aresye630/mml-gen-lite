# 如何确保约束生效（讨论稿）

## 问题

prompt 是「建议」，不是「约束」。实测证据：
```
GT 6445 条中 RMV 980 条（15.2%）
产物 1600 条中 RMV 196 条（12.2%）

但 10 个有删除意图的工单里：
  NC20260820000552  GT 339 条 RMV → 产物 0 条 RMV
  NC20260828001156  GT 280 条 RMV → 产物 0 条 RMV
  NC20260803001614  GT  91 条 RMV → 产物 0 条 RMV
→ prompt 对多数 case 无效
```

## 五种约束手段，可靠性递进

| 手段 | 可靠性 | 说明 |
|---|---|---|
| 1. prompt 文字 | ❌ 低 | 靠运气，实测多数失效 |
| 2. 判据 warn | ❌ 无 | 只提示，不改 |
| 3. 判据 fatal | ⚠️ 中 | 会回炉，但可能死循环 |
| 4. **结构化输入** | ✅ 高 | 格式强制，无歧义 |
| 5. **程序化修正** | ✅✅ 最高 | 代码直接改，确定 |

## 具体方案：按问题类型选手段

### 问题 A：意图说删除，agent 配成新增

**根因**：意图里【删除】段落是自然语言，agent 要自己解析成动词。

**方案 4（结构化输入）**：
第 1 步，代码先从意图里解析出「操作清单」：
```yaml
operations:
  - verb: RMV
    targets: [接口, 会话, 区段, 业务接口IPv4地址]
  - verb: ADD
    targets: [区段, 接口, IP绑定VPN, 业务接口IPv4地址]
```
第 2 步，把这份清单作为独立的输入文件给 agent（不是塞在意图文本里）。
第 3 步，G18 增强：意图说 RMV 的族，产物必须有对应 RMV 命令。

**关键**：解析是代码做的，不是 agent 做的。代码解析【删除】段落里的名词 → 映射到族名（用 kb 知识库）。

### 问题 B：agent 擅自缩小范围

**根因**：agent 发现「配不了」时自己决定不做。

**方案 5（程序化检测）**：
- 检测 agent 的产物里有没有「我用 XXX 代替」「不配置」「跳过」这类措辞
- 检测配置分析.md 里的「风险」「不做」段落
- 有的话强制走 clarify（不管 agent 想不想）

**更彻底**：agent 输出的每个族都必须有来源标注。
```
族缺席时，必须在 方案澄清.json 里有对应条目
否则判「未说明的省略」→ 提示用户
```

### 问题 C：ADD vs MOD 混淆

**根因**：agent 不知道现网有没有该对象。

**方案 5（程序化修正）**：
```
展开后，代码检查每条 ADD 命令的主键：
  如果该主键在 EXP 里已存在 → 自动改成 MOD
  如果 agent 用了 MOD 但主键不存在 → 提示（可能是要 ADD）
```
**这个可以完全程序化，不需要 agent 参与。**

### 问题 D：大工单只出样本

**方案 4（结构化）**：模板展开机制（已实现）

## 我的建议顺序

```
1. 问题 C（ADD/MOD 自动纠正）—— 纯程序，零风险，先做
2. 问题 A（意图结构化解析）—— 需要 kb 支持名词→族名映射
3. 问题 B（省略检测）—— 检测 + 强制澄清
4. 问题 D —— 已有机制，补 prompt 引导用模板
```
