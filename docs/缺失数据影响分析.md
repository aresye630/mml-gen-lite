# 缺 SET / RMV / MOD 所需数据的影响分析

> 2026-11-10  
> 场景：部分工单的 EXP 是样例而非完整现网配置，且部分网元（SMF）的 EXP 未能提供

---

## 一、三类命令对「现网数据」的依赖程度完全不同

| 命令类型 | 本质 | 需要现网数据吗 | 缺数据的后果 |
|---|---|---|---|
| **ADD** | 新建对象 | **不需要**（对象本来就不存在） | 无影响 |
| **SET** | 改已有对象的属性 | **需要**（要知道对象存在 + 现有哪些属性） | agent 不知道对象存在，**直接跳过不配** |
| **MOD** | 改已有对象的属性 | **需要**（同 SET） | 同 SET，且 MOD 通常**要求列出全部参数**，缺现网值会乱填 |
| **RMV** | 删已有对象 | **需要**（要知道对象存在 + 完整主键） | agent 不知道要删什么，**漏删** |

**结论：ADD 不依赖数据，SET/MOD/RMV 强依赖数据。**

---

## 二、实测：44 个缺失族的动词分布

| 动词 | 族数 | 占比 |
|---|---|---|
| **SET** | 25 | 57% |
| **MOD** | 9 | 20% |
| ADD+RMV | 7 | 16% |
| **RMV** | 3 | 7% |

**SET 是最大头（57%）。**

## 三、逐类影响推演

### 3.1 SET 类（25 族）——影响：静默跳过，功能缺失

**典型命令：**
```
SET APNCHARGECTRL: APN="sos", ONLINESW=INHERIT, OFFLINESW=INHERIT,
                   CCNAME="imscc", CCTEMPLATE="ims_offline_cc"...
SET APNIDLETIME:   APN="sos", INHERIT=NO, SCTXCHKSW=ENABLE...
SET APNPCCFUNC:    APN="sos", HOMEPCCSWITCH=ENABLE, PCCTEMPLATE="ims_pcc_tmp"...
SET AMFSOFTPARAOFBIT: DT=Dw, DWORDNUM=70, VALUE=VALUE_1, POSITION=28
```

**影响机制：**
1. 这些命令的主键是 `APN="sos"`、`DT=Dw+DWORDNUM=70` 这类**已存在的对象**
2. agent 拿不到 EXP，就**不知道 `APN="sos"` 这个对象存在**
3. agent 大概率**完全不生成这条命令**（不是生成错的，是根本没有）
4. 结果：配置看起来「少了几条」，但因为没有对比基准，用户很难发现

**危害等级：中高**
- 不会产生错误配置（不会配坏）
- 但会**静默缺失**——功能不生效，且不易察觉
- 这类缺失在真实运维中是**最危险的**，因为上线后才发现功能不对

**具体影响举例（NC20260811002706）：**
```
缺 SET APNCHARGECTRL  → 新建 APN "sos" 时没配计费策略
                        → 该 APN 用户上网不计费 / 计费走默认策略
缺 SET APNPCCFUNC     → 没配 PCC 功能开关
                        → 策略控制不生效
缺 SET APNIDLETIME    → 没配空闲定时器
                        → 会话可能提前释放或长期占用
```

### 3.2 MOD 类（9 族）——影响：要么跳过，要么填错值

**典型命令：**
```
MOD CONNECTPLMN: MCC="202", MNC="10", EMCBS=NO, EMGCNUMSW=OFF;
MOD HPLMN:       MCC="460", MNC="00", EMCBS=NO, EMGCNUMSW=OFF;
MOD NGCONNECTPLMN: NOID=0, MCC="454", MNC="12", EMG=EMFNR-0&EMCNR-0;
```

**影响机制：**
1. MOD 需要知道**主键 + 要改的参数 + 现网原值**
2. 缺 EXP 时 agent 有三种可能行为：
   - a) 跳过不配（最常见）
   - b) 自己编一个主键（如 `MCC="460", MNC="00"`），可能配到不存在的对象上 → **报错**
   - c) 只填改动的参数，其他留空 → **可能把其他参数改成默认值**

**危害等级：高**
- 情况 b 会**配置失败**（对象不存在）
- 情况 c 更危险：MOD 命令如果只写部分参数，某些产品会把未写的参数重置为默认值 → **误删了其他配置**

**具体影响举例（NC20260810002261）：**
```
缺 MOD CONNECTPLMN 343 条  → 343 个 PLMN 的 EMCBS/EMGCNUMSW 开关没改
                            → 紧急呼叫支持位没按地域调整
缺 MOD HPLMN 7 条           → 归属 PLMN 的紧急呼叫开关没改
```

**注意：CONNECTPLMN 单族 343 条，占该工单 GT 的 79%（436 条里 343 条）。这一个族的缺失直接决定了这个工单的成败。**

### 3.3 RMV 类（3 族）——影响：漏删，旧配置残留

**典型命令：**
```
RMV FILTER:        FILTERNAME="xxx";
RMV FLTBINDFLOWF:  FLOWFILTERNAME="yyy", FILTERNAME="xxx";
RMV HOST:          HOSTNAME="zzz";
RMV UPBINDUPG:     USERPROFGNAME="upg_sos";
RMV USRPROFGROUP:  USERPROFGNAME="upg_sos";
```

**影响机制：**
1. RMV 需要知道**要删什么**——完整主键（多个参数）
2. 缺 EXP 时，agent 只有意图里的业务描述（如「删除用户模板组」），**不知道具体名字**
3. agent 要么跳过，要么编一个名字去删（→ 删不到东西，或删错）

**危害等级：中**
- 跳过：旧配置残留，一般不影响新功能，但会占资源/留下隐患
- 编错名字：RMV 一个不存在的对象通常报错，不会误删

**但有一个例外：删除类变更的完整性要求**
```
RMV FLTBINDFLOWF → RMV FILTER → RMV HOST
删除有严格顺序（先解绑再删主对象）
缺数据时 agent 不知道有绑定关系，可能只删了主对象
→ 留下孤儿绑定，某些产品会告警或拒绝删除
```

### 3.4 ADD+RMV 混合（7 族）——影响：删除部分丢失

```
UPBINDUPG    GT: ADD 2 条 + RMV 1 条（先删旧绑定再加新绑定）
USRPROFGROUP GT: ADD 2 条 + RMV 1 条
MMEIPTOMMEPOOL GT: ADD 8 条 + RMV 8 条（16 条）
LICX1INFO/2INFO  GT: ADD 5 + RMV 5
```

**影响：**
- ADD 部分不影响（新建对象）
- **RMV 部分受影响**（不知道删哪些）
- 结果：新配置加上了，但旧的没删 → **新旧并存，可能冲突**

**危害等级：中高**（特别是 MMEIPTOMMEPOOL 这种 8 删 8 加的，删错了会导致地址池混乱）

## 四、对评估指标的影响（关键）

**当前评估方式的问题：**

```
如果 GT 里有 44 条 SET/MOD/RMV 因缺数据配不出来
→ 这些命令会被算作「agent 漏配」
→ 但实际是「数据没给，不可能配出来」
→ 评估结果**低估了 agent 的真实能力**
```

**具体影响量化（以 NC20260810002261 为例）：**

| 项 | 数值 |
|---|---|
| GT 命令总数 | 436 条 |
| 缺数据的族对应的命令 | **354 条**（CONNECTPLMN 343 + HPLMN 7 + NGCONNECTPLMN 3 + NGNILRPARA 1）|
| 占比 | **81%** |
| 理论最高命令完成度 | 只剩 **19%** |

**这个工单无论 agent 多聪明，命令数上限就是 19%。** 但之前的评估报告里，它是按「436 条全要求」算的，所以显示 8% 完成度——看起来像 agent 很差，实际是数据问题。

## 五、建议的处理方式

### 5.1 评估口径：按「可评估命令数」算，不按 GT 全量算

```
对每个工单：
  GT 总命令数         T
  缺 SET/MOD/RMV 数据的命令数  M（这些不可能配出来）
  可评估命令数         T - M

评估：
  族覆盖   = 命中族 / 可评估族（ADD 族 + 有数据的 SET/MOD/RMV 族）
  命令数   = 产物命令 / (T - M)
```

**注意：ADD 族仍然要算进去**，因为新建不需要现网数据。

### 5.2 报告里明确标注「数据受限工单」

```
工单 NC20260810002261：
  GT 436 条，其中 354 条需要 SMF 侧 EXP（未提供）
  → 可评估 82 条，产物 37 条 = 45%（而不是 8%）
  → 标注：本单 81% 的 GT 命令无法评估
```

### 5.3 对 agent 的提示（已有 G27 覆盖）

G27 已经要求 agent 写「本网元无法配置的项」。对于缺 SMF 数据的工单，agent 应该：
```
## 本网元无法配置的项
| CONNECTPLMN 修改 | 343 条 | 本工单只有 AMF 的 EXP，无 SMF | 需 SMF 网元操作 |
```

**这样用户能看到「不是没配，是配不了」。**

## 六、样例数据（非完整配置）的影响

用户提到「有的 UDG 也是样例，不是完整的数据配置」。这带来额外问题：

**如果是样例数据：**
```
EXP 里只有部分对象（比如 1000 个 APN 里只导出了 10 个）
→ agent 查不到某个 APN，会认为它不存在
→ 可能用 ADD 新建（实际已存在）→ G23 会报「ADD 已存在对象」但查不到
→ 或者跳过
```

**危害：比「完全没有」更隐蔽**
- 完全没有：agent 会明确报告「本网元无此族」
- 样例数据：agent 可能误判「对象不存在」，进而做出错误决策

**建议：**
1. 在数据清单/意图里明确标注「EXP 为样例，对象清单以数据清单为准」
2. 或者让 agent 在配置分析里写「现网未查到 XXX，按意图新建」

---

## 七、结论

| 类别 | 族数 | 影响 | 危害 |
|---|---|---|---|
| **SET** | 25 | 静默跳过，功能不生效 | **中高**（不易发现）|
| **MOD** | 9 | 跳过或误改其他参数 | **高**（可能配置失败）|
| **RMV** | 3 | 漏删，旧配置残留 | 中 |
| ADD+RMV | 7 | 删旧部分丢失，新旧并存 | 中高 |
| ADD | 67 | 无影响 | 无 |

**核心结论：**
1. **44 个真缺数据的族对应约 400+ 条命令，主要集中在 5 个跨网元工单**
2. **这些命令 agent 不可能配出来，评估时必须从分母里剔除**
3. **SET 类最危险**——不会报错，但功能静默失效
4. 当前评估口径（按 GT 全量算）**严重低估**了这些工单的真实能力
