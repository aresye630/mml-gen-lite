# 算子扩展机制设计（讨论稿）

## 问题

现有 7 个固定算子（IDENTITY / PREFIX_REPLACE / PREPEND / APPEND / CONCAT / MAP / SEQ）
实测覆盖真实配对关系的 77.3%，剩 22.7% 无法描述。

## 三层方案

### 第 1 层：固定算子（已实现）
覆盖 77%，零开销，完全确定性。

### 第 2 层：算子组合
现有算子可以串联，能覆盖更多：
```
grp-sos-smf001-deft → map-sos-smf001-deft-2g
= PREFIX_REPLACE(grp,map) | APPEND(-2g)
```

**这层已经支持，实际覆盖率比 77% 更高**（我的统计没算组合）。

### 第 3 层：受限脚本算子（可选）
当组合也写不出来时，允许 agent 提交一个**受限 Python 表达式**：
```yaml
SCRIPT: "x.replace('grp','map') + '-' + ctx['制式']"
```

**安全约束**：
1. 只允许字符串方法和算术，禁止 import / 函数定义 / 属性访问
2. 用 AST 白名单校验，不通过就拒绝
3. 沙箱执行，超时 1 秒

**开销**：只在首次遇到无法描述的配对时发生一次。

## 我的倾向：先不做第 3 层

理由：
1. **77% 已经覆盖主要场景**，剩下的多是噪音（我统计里的 PARTIAL_MATCH 大多是误配）
2. **算子在代码里是确定性的**，一旦引入动态脚本，就破坏了「代码侧可完全复现」这个性质
3. **agent 写错的代价高**：脚本写错不会报语法错，会静默生成错误的值

## 替代方案：让 agent 换策略

当遇到无法描述的派生时：
```
agent 发现：pool 名无法用算子从池组名推出
→ 改成：把 pool 名作为用户 CSV 的一列（让用户直接给）
→ 或者：在方案澄清里说明「需要人工确认这些名字」
```

**这比动态加算子更符合「人不给命令语义」的原则。**
