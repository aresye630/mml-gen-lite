## 二、优化的三个阶段

### 阶段 1：MCP 层缓存（提交 5134d0abe）

| 改动 | 文件 | 效果 |
|---|---|---|
| EXP 解析 + 结果缓存 | `mcp_exp.py` | 45MB EXP 冷查 3.69s → 热查 0.00s |
| KB 检索缓存 | `mcp_knowledge.py` | 重复查询 0.00s |
| Guard 解析缓存 | `guard.py` | 4.74s → 2.72s |
| 修复 `emit` 被覆盖 bug | `agent_run.py` | 修掉 `TypeError: 'dict' object is not callable` |
| max_tokens 1024→8192 | 容器配置 | 单次可输出 200 行 CSV |

### 阶段 2：Guard 深度优化（提交 1cff9b31e）

**问题链**：`guard_check` 每次 24.4s

```
mcp_io 用 subprocess 起新进程
  → 新进程重读 45MB EXP 全量解析
  → G17 对 12 万条命令逐条 split_cmd（6.46s）
  → G12 内部重跑 parse_mml（4.70s）
```

**修法**：

1. `G17` 加 `_fam_count` 缓存（只算 verb+family，不解析参数）
2. `G12` 加 `_G12_CACHE`（同输入结果相同）
3. `mcp_io` 改进程内 `import guard`（缓存跨调用复用）
4. **缓存 key 用内容哈希而非 `id(text)`**

**结果**：24.4s → 7.7s（冷）→ 2.8s（热）

### 阶段 3：KB 进程内调用

**问题**：`kb_search_command` 每次 1.37s

```
_run_script 每次 subprocess 起新进程
  → 脚本模块级 `emb = Emb()` 加载嵌入模型 → 1.3s
```

**修法**：进程内 import，复用已加载的模型和 DB 实例

**结果**：8 个命令 10.92s → 5.82s

## 五、踩坑记录

| 坑 | 现象 | 原因 | 修法 |
|---|---|---|---|
| **`emit` 被覆盖** | `TypeError: 'dict' object is not callable`，偶发 | 第 839 行写成 `emit = {...}`，把函数覆盖成 dict | 改名为 `_ev_round_start` |
| **docker cp 不生效** | 改了代码但验证结果不变 | 后端进程已加载旧模块到内存 | 必须 `docker restart` |
| **`importlib.reload` 清缓存** | 进程内调用反而 8.5s | reload 重新执行模块，清空所有 cache | 去掉 reload |
| **`id(text)` 做缓存 key** | 缓存永不命中（每次大小都涨） | 每次 `read_text()` 产生新对象，id 不同 | 改用 `hash(text)` |
| **变量名写错静默回退** | 改了进程内调用但没生效 | 写了 `WF_ROOT`（实际是 `WORKFLOW_ROOT`），except 静默回退子进程 | 加日志或断言 |
| **Write 次数降不下来** | prompt 改 150-200 行无效 | agent 有自己的写节奏，即使 max_tokens 够大 | 收益有限，只降 20% |

## 六、后续优化方向

### 已到上限

```
Write 合并：Write 本身 0s，只是 LLM 往返，砍不掉
EXP 合并：缓存后每次 1.6s，159 次 = 236s，已不是瓶颈
```

### 仍有空间

| 方向 | 预期收益 | 难度 |
|---|---|---|
| **减少 LLM 往返次数** | 大 | 需改 agent 行为模式 |
| **合并 KB 查询** | 100-150s | 中（新增批量工具） |
| **Guard 继续优化**（12.6s → 2.8s 的热态还没完全体现） | 50-80s | 低 |
| **换更快的模型** | 不确定 | 低 |

### 关键洞察

```
工具优化已从 58% 降到 32%
剩下的 68% 是 LLM 推理时间
→ 继续优化工具，总收益上限只有 32%
→ 要进一步提升，必须减少 LLM 往返次数或换模型
```
