# 阶段3：一致性修复 workflow（设计稿）

> 2026-11-12
> 用户裁定：按需触发 / 属性族直接配+注释 / params.csv 与 mml.txt 必须一致（重跑生成器）

## 一、为什么需要阶段3

现有链路的问题（实测数据）：

```
NC20260810002261（GT 53 族）6 次运行：
  规划命中  33 / 13 / 31 / 14 / 17 / 2 族   ← 波动 16 倍
  产物命中  26 / 33 / ...                  ← 也不稳定
  6 次运行的并集 40/53，交集 0/53           ← 没有稳定命中的族
```

根因：prompt 里 30+ 条要求全靠 agent 自觉，每次执行一部分。
- 有的运行用 62 行逐族列，有的用 11 行通配概括
- 有的运行调了 exp_cross_stats 判网元，有的凭感觉猜
- 有的运行配了属性族链，有的只配主体族

**阶段3 的定位：把 prompt 里的要求从「文字」变成「workflow 步骤」，每步有明确的输入/输出/判据，不做自由发挥。**

## 二、触发条件（按需）

```python
def should_run_stage3(session_dir, plan_txt, mml_txt):
    """返回 (bool, reason)"""
    # 触发条件（任一命中即跑）
    triggers = []

    # 1) 大单：GT 族数多（用规划行数代理）
    n_rows = count_plan_rows(plan_txt)
    if n_rows >= 15:
        triggers.append(f'规划表 {n_rows} 行，属大单')

    # 2) 规划表有通配（G31）
    if has_wildcard(plan_txt):
        triggers.append('规划表用了通配/概括')

    # 3) guard 报了与「漏配」相关的 warn（G25/G27/G29/G30/G31）
    warns = [g for g in guard_results if g.severity == 'warn' and g.id in LEAK_IDS]
    if warns:
        triggers.append(f'guard 报了 {len(warns)} 条漏配相关 warn')

    # 4) 阶段2 产物族数 < 规划表族数（说明规划了没配）
    if n_prod_fams < n_plan_fams:
        triggers.append(f'产物 {n_prod_fams} 族 < 规划 {n_plan_fams} 族')

    return (len(triggers) > 0, triggers)
```

**小单（规划 <15 行、无通配、无 warn）不跑阶段3，省时间。**

## 三、Workflow 六个步骤

### Step 1：规划表结构合规（纯代码，<1s）

```python
检查项：
  □ 状态列取值 ∈ {确认, 待定, 跳过}
  □ 命令族列无通配（复用 G31 逻辑）
  □ 判断依据非空且含现网证据（行号/条数/参数值）
  □ 没有把族写成散文（检查「不确定项」段落里有没有族名）

修复（代码）：
  · 状态非法 → 归一化（含「确认」→确认，含「待定」→待定）
  · 有通配 → 交给 Step 3 展开（不在本步修）
  · 散文里的族 → 提取成表行（正则 + 状态=待定）
```

### Step 2：意图对象覆盖（1 次 LLM + 代码校验）

```python
输入：意图原文
LLM 任务（只用一次，输出结构化）：
  「从意图里提取所有业务对象，输出 JSON：
   [{group: '【APN 与移动性】', object: 'APN「sos」', family_hint: 'APN'}]
   只提取对象，不要判断该配什么族。」

代码校验：
  · 每个 object，规划表里有没有对应行（按 object 名或 family_hint 匹配）
  · 没有 → 记入 missing_objects

修复（代码 + 1 次 LLM）：
  · 对 missing_objects，调 exp_query 搜现网
  · 找到族 → 生成规划行（状态=待定，判断依据=exp 行号）
  · 找不到 → 生成规划行（命令族列写「未找到」，状态=待定）
```

### Step 3：属性族链补齐（纯代码 + EXP 工具，~15s）

```python
输入：规划表里所有「对象族」（如 APN / USERPROFILE / POOL）
代码：
  for obj_family in plan_object_families:
      r = exp_attr_chain(path=EXP, owner_family=obj_family)
      for attr_fam in r.attribute_families:
          if attr_fam not in plan_families:
              missing_attrs.append((obj_family, attr_fam))

修复（代码生成，不调 LLM）：
  · 每个 missing_attr 生成一行：
      命令族 = SET <ATTR_FAM>
      动作   = 新增
      判断依据 = f'{obj_family} 的属性族链，现网 {n} 条，见 exp_attr_chain'
      状态   = 确认      ← 按用户裁定：直接配
```

### Step 4：规划表 → 产物一致性（纯代码）

```python
输入：规划表（状态=确认）+ params.csv + mml.txt
检查：
  · 规划表每行 → params.csv 里有对应组吗？
  · params.csv 每组 → mml.txt 里有命令吗？

修复：
  · 缺的组 → 用 exp_query(owner=<obj>, value=<实例>) 拿现网写法
             → 按模板填 params.csv（值来自现网 or 数据清单）
  · params.csv 改了 → 必须重跑生成器（用户裁定）
```

### Step 5：prompt 硬要求逐条核对（复用已有判据，<5s）

```python
复用 guard 已有判据，把 warn 变成「待修清单」：

  G12 命名规律      → 命名不符现网 → 改 params.csv
  G18 参数齐全      → 缺必选参数   → 补 params.csv
  G22 占位符        → 占位符过多   → 能用现网值就补，补不了保留
  G25 配套族        → 缺配套族     → 补规划行
  G27 跨网元        → 配不了的项   → 写进「本网元无法配置的项」
  G29 SET 属性族    → 规划有产物无 → 补 params.csv
  G30 RMV vs ADD    → 方向反了     → 改动词
  G31 规划表通配    → 已在 Step 3 处理
```

### Step 6：补配清单 + 重跑生成器（代码）

```python
输出 repair_report.md：
  ## 补配清单
  | 来源步骤 | 补了什么 | 依据 | 是否需人工确认 |
  |---|---|---|---|
  | Step 3 | SET APNCHARGECTRL（APN sos） | 属性族链，现网 333 条 | 否 |
  | Step 3 | SET APNIDLETIME（APN sos）   | 属性族链，现网 333 条 | 否 |
  | Step 2 | ADD NGHPLMN                  | 意图「调整互联PLMN」| 是（PLMN 值未给）|

  ## 多配警告（按用户要求：标注释让用户删）
  mml.txt 里补配的命令都加注释：
    SET APNCHARGECTRL: APN="sos", ...;  // @stage3=属性族链补齐 现网333条
  → 用户 review 时可以一眼看出哪些是自动补的，多余的直接删

然后重跑生成器：
  mml_gen.py --params params.csv --out mml.txt
```

## 四、关键设计：属性族直接配 + 注释标记

按用户裁定，属性族不标「待定」，直接配，但加注释：

```mml
// ===== 以下命令由阶段3 自动补齐（属性族链），请确认是否本次需要 =====
SET APNCHARGECTRL: APN="sos", CCNAME="imscc", ...;   // @stage3=attr_chain 现网333条
SET APNIDLETIME: APN="sos", TIMER=600, ...;          // @stage3=attr_chain 现网333条
// ===== 阶段3 自动补齐结束 =====
```

**理由（用户）：**
> 让用户删比让用户再补意图交互要简单

## 五、params.csv 与 mml.txt 一致性（必须重跑）

```
阶段3 的所有修复都改 params.csv
→ 改完必须调 mml_gen.py 重新生成 mml.txt
→ 不允许直接改 mml.txt

理由（用户）：params 要和 mml 一致，这个不能省
```

## 六、性能估算

### 各步骤耗时（基于实测）

| Step | 内容 | 耗时来源 | 估算 |
|---|---|---|---|
| Step 1 | 结构合规 | 纯代码 | <1s |
| Step 2 | 意图对象提取 | 1 次 LLM | **30-45s** |
| Step 3 | 属性族链 | exp_attr_chain 冷 13.7s + 热 0ms | **15-20s** |
| Step 4 | 一致性 + 补命令 | exp_query 0.01s/次 | **5-10s** |
| Step 5 | 判据核对 | 复用 guard | <5s |
| Step 6 | 重跑生成器 | mml_gen.py | **2-5s** |
| 修复轮次 | 需要 LLM 的场景 | 每轮 30-60s | **0-2 轮** |

### 总计

```
无 LLM 修复（理想情况）：1 分钟
有 1 轮 LLM 修复：     2 分钟
有 2 轮 LLM 修复：     3 分钟
```

**不是 10-20 分钟。** 我之前估错是因为把整个阶段3 想成一次 agent 自由执行（要重新读 EXP、重新理解意图）。

Workflow 化的关键收益：
- EXP 解析复用缓存（冷 13.7s 一次，之后 0ms）
- 大部分判断是代码，不占 LLM
- LLM 只用在「提取对象清单」和「无法代码化的修复」

### 整体性能劣化

| 场景 | 现在（阶段1+2） | 加阶段3 | 劣化 |
|---|---|---|---|
| 小单（不触发） | 180-400s | 180-400s | **0%** |
| 大单（触发） | 900-2600s | 960-2660s | **+2-7%** |
| 全量 85 单 | 约 4 小时 | 约 4.1 小时 | **+2.5%** |

**结论：按需触发下，整体性能劣化约 2-3%，可接受。**
