## 二、LLM 校验 loop 方案

### 2.1 设计

```
agent 生成产物
   ↓
规则判据（G11-G29，快、确定、零成本）
   ↓ 有 fatal / warn
LLM 校验器（逐条检查 prompt 要求）
   ↓
输出「未满足的要求清单 + 证据（行号）」
   ↓
回炉给 agent 修
   ↓
最多 N 轮
```

### 2.2 LLM 校验器要检查什么

**不是把整个 prompt 丢给 LLM 让它自由发挥**，而是把 prompt 要求拆成结构化清单，逐条问 LLM「这条满足了吗？给出行号证据」。

```python
CHECKS = [
    {
        'id': 'R1',
        'requirement': '删除对象必须用 RMV，不能用 ADD',
        'how': '扫产物里所有 ADD 命令，判断意图是否要求删除这些对象',
        'input': ['意图全文', '产物 mml'],
        'judge': '有没有 ADD 实际应该是 RMV 的对象？列出族名和行号',
    },
    {
        'id': 'R2',
        'requirement': '意图点名的每个业务对象都要有对应的族',
        'how': '把意图里的每个【】分组条目和规划表的行做配对',
        'input': ['意图全文', '命令族规划.md'],
        'judge': '有没有意图提到但规划里没有对应行的条目？',
    },
    ...
]
```

### 2.3 成本估算

| 项 | 数值 |
|---|---|
| 单次校验输入 | 意图（~500字）+ 产物摘要（~3000字）≈ 4000 tokens |
| 单次校验输出 | ~500 tokens |
| 每条要求一次调用（或全部打包一次） | 打包：1 次调用 / 工单 |
| 87 工单 × 2 阶段 | 174 次额外调用 |
| 单次耗时 | ~5-10s |
| 总额外耗时 | 15-30 分钟（4 容器并发 → 4-8 分钟）|

**成本可接受，但要注意：curator 的教训是「178 次额外调用把主任务拖到 3000s 超时」。这里的额外调用在同一进程内串行，不会抢配额到那个程度。**

### 2.4 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **LLM 校验本身不可靠** | 用 LLM 判断 LLM 的输出，可能一路放行 | 必须要求给行号证据；无证据不放行 |
| **误报导致回炉** | 校验器误判 → agent 反复修 → 轮次耗尽 | 只做 warn 不做 fatal；最多回炉 1 次 |
| **成本膨胀** | 每轮都校验 | 只在最后一轮校验一次 |
| **循环依赖** | 校验器的 prompt 又要遵守什么？ | 校验器只做「结构化比对」，不做开放式判断 |

## 三、我的判断

**方向对，但要严格控制范围。**

### 值得做的
```
1. R1（RMV vs ADD）—— 这是实测 10 单 8 单错的高频问题，规则判据做不了
   （需要理解意图），只能靠 LLM
2. R2（意图条目 vs 规划行）—— 本质是「覆盖度检查」，
   但意图是自然语言，规则匹配不准
```

### 不值得做的
```
3. 把「参数名要核对」「命名按现网规律」这类交给 LLM 校验
   —— G12/G19 规则判据已经很准，LLM 只会更慢更贵
4. 每条 prompt 要求都校验 —— 12 条 × 174 工单 = 2088 次调用，太贵
```

### 建议实施
```
方案：单次调用的「结构化清单校验」
  · 一个固定 prompt，内含 4-5 条可 LLM 判定的要求
  · 输入：意图 + 产物摘要（族列表 + 命令数 + 关键行号）
  · 输出：JSON [{requirement_id, satisfied, evidence_lines, explanation}]
  · 只做 warn，不阻断
  · 只在阶段2 最后一轮做一次
```

## 四、与现有判据的关系

```
规则判据（G11-G29）  →  确定性检查，pytest 可复现，零成本
LLM 校验（R1-R5）    →  语义检查，成本高，结果不稳定

优先级：能用规则判据的，坚决不用 LLM 校验
      规则做不了的（涉及意图理解），才用 LLM
```

**目前只有 R1（RMV vs ADD）和 R2（意图覆盖度）真的需要 LLM。**
