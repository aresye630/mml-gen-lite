### exp_stats 四层模型（2026-11-11 重写）

```
第一层 操作        ADD / MOD / SET / RMV
第二层 对象与身份   object_families    有 ADD 的族（能独立创建，identity_param 是主键）
                  attribute_families 只有 SET/MOD/RMV 的族（挂在 owner_family 上）
第三层 引用关联    references = {族: [{param, target_family, n}]}
第四层 行为参数    enums / priority_range（不含身份和引用参数）
```

**修复的关键 bug**：旧版 `if v != 'ADD': continue` 导致 82% 的族（1098/1345）不可见。
修复后实测：单 EXP 从 61 族 → 473 族，GT 覆盖率从 12.9% → 100%。

### exp_query owner 模式（2026-11-12 新增）

```python
exp_query(path, owner="APN", value="ims.wh")
→ 一次返回 APN 及其 23 个属性族针对 ims.wh 的完整命令
```

# 第二部分：核心问题（实测数据）

## 2.1 阶段1 波动是最大问题

同一单、同一意图、同一 prompt，6 次运行结果：

| 工单 | GT 族 | 6 次运行结果 | 波动 |
|---|---|---|---|
| NC20260810002261 | 53 | 33 / 13 / 31 / 14 / 17 / 2 | **16 倍** |
| NC20260806001780 | 41 | 23 / 17 / 12 / 16 / 24 / 13 | 2 倍 |

**6 次运行的并集 40/53，交集 0/53 —— 没有一个是每次都能命中的族。**

## 2.2 波动的三个来源（已定位）

### 来源1：规划表粒度不定

```
有的运行写 62 行（逐族列）
有的运行写 11 行（用 SET APN* 概括 25 个族）
→ 阶段2 拿到不同粒度的表，产出差异大
```

**G31 已能检测（实测 3/11 个规划表有通配）。**

### 来源2：网元归属判断随意

```
NC20260810002261 一次运行判断「APN 只在 UDG」（错，UNC 有 333 条）
另一次判断正确（调了 exp_cross_stats）
```

### 来源3：分析深度不定

```
做得多的：exec 29 次 + exp 33 次 → 33/53
做得少的：exec 5 次 + exp 6 次  → 14/53
```

## 2.3 阶段2 有修复能力但不稳定

| 工单 | 规划命中 | 产物命中 | 阶段2 补的 | 阶段2 漏的 |
|---|---|---|---|---|
| NC20260806001780 | 17/41 | 34/41 | **+17** | 0 |
| NC20260810002261 | 33/53 | 26/53 | +5 | **-12** |

**阶段2 能补 17 个族，也能漏 12 个族 —— 都是自由发挥的结果。**

## 2.4 「照着配」的信息完整度（86 单）

| 组合 | 单数 | 占比 | 处理方式 |
|---|---|---|---|
| 参照对象 + 业务段都有 | 15 | 17% | 直接走参照流程 |
| 只有业务段 | 17 | 20% | 自动选参照 |
| 只有参照对象 | 4 | 5% | 澄清问业务段 |
| **两者都无** | **50** | **58%** | **不需要参照（新建对象）** |

# 第三部分：阶段3 设计（本次实现）

## 3.1 定位

```
阶段3 = consistency repair workflow
目标：把 prompt 里的 30+ 条要求，从「文字」变成「可执行的检查 + 修复」
原则：确定性优先，不做自由发挥
```

## 3.2 触发条件（按需）

```python
def should_run_stage3(intent_text, plan_txt, guard_results, prod_fams, plan_fams):
    triggers = []

    # 条件1：意图条目数 >= 11（覆盖 GT 族中位 >= 8 的工单，占 37%）
    #   实测相关性：意图条目数 vs GT 族数 = 0.986
    n_items = len(re.findall(r'^-\s', intent_text, re.M))
    if n_items >= 11:
        triggers.append(f'意图 {n_items} 条，属中大型')

    # 条件2：规划表有真通配（G31）
    if has_wildcard(plan_txt):
        triggers.append('规划表用了通配/概括')

    # 条件3：guard 报了漏配类 warn（G25/G27/G29/G30/G31）
    leak = [w for w in guard_results if w.id in LEAK_IDS]
    if leak:
        triggers.append(f'guard 报 {len(leak)} 条漏配 warn')

    # 条件4：产物族数 < 规划表族数
    if prod_fams < plan_fams:
        triggers.append('产物族数少于规划族数')

    return len(triggers) > 0, triggers
```

**阈值 11 的依据**（86 单分档）：

| 意图条目 | 单数 | GT 族中位 | GT 条中位 |
|---|---|---|---|
| 1-5 | 38 | 2 | 8 |
| 6-10 | 16 | 7 | 45 |
| **11-20** | **21** | **12** | **128** |
| 21-40 | 6 | 30 | 73 |
| >40 | 5 | 54 | 765 |

## 3.3 六步 workflow

### Step 1 规划表结构合规（纯代码，<1s）

```
检查：
  □ 状态列取值 ∈ {确认, 待定, 跳过}
  □ 命令族列无通配（复用 G31）
  □ 判断依据非空且含现网证据（行号/条数/参数值）
  □ 散文段落里有没有族名（应该写成表行）

修复（代码）：
  · 状态非法 → 归一化
  · 散文里的族名 → 提取成表行（状态=待定）
```

### Step 2 意图对象覆盖（纯代码，<0.1s）

```
前提：意图是 V3 格式（结构规整），可纯代码提取。
      若是自然语言意图（V1），退化为 1 次 LLM 提取。

提取规则：
  按【】切分组
  每行匹配 ^-\s*(新增|调整|删除|设置)\s+(.+?)(（.*）)?$
  obj = 第 2 组（去约束）
  从约束里找「XXX 名称为 YYY」→ 提取实例名

检查：
  每个 object，规划表里有没有对应行？

修复：
  没有 → 调 exp_query 搜现网
        找到族 → 生成规划行（状态=待定，依据=exp 行号）
        找不到 → 生成规划行（命令族写「未找到」）
```

### Step 3 属性族链补齐（纯代码 + EXP 工具，~15s）

```
检查：
  for obj_family in plan_object_families:
      r = exp_attr_chain(path=EXP, owner_family=obj_family)
      for attr_fam in r.attribute_families:
          if attr_fam not in plan_families:
              missing_attrs.append((obj_family, attr_fam))

修复策略（用户裁定：C 两阶段）：
  ① 参照法：参照对象（如 ims.wh）配过的族 ∩ 数据清单提及的 → 直接配（状态=确认）
  ② 其余属性族 → 配但标「待定」+ 注释标记

实测数据（决定为什么先用参照法过滤）：
  NC20260810002261  EXP 里 APN 属性族 56 个，GT 只要 12 个
  · 全量配：多余 45 个族
  · 参照 ims.wh：26 个族，命中 GT 9 个，多余 17 个
  · 参照 ∩ 数据清单：多余 8 个左右
```

### Step 4 规划表 → 产物一致性（纯代码 + exp_query，~5-10s）

```
检查：
  · 规划表每行（状态=确认） → params.csv 里有对应组吗？
  · params.csv 每组 → mml.txt 里有命令吗？

修复：
  缺的组 → exp_query(owner=<obj>, value=<实例>) 拿现网写法
          → 按模板填 params.csv
          → 必须重跑 mml_gen.py（用户裁定：params 与 mml 必须一致）
```

### Step 5 prompt 硬要求逐条核对（复用 guard，<5s）

```
把 guard 已有判据的 warn 变成「待修清单」：

  G12 命名不符现网   → 改 params.csv
  G18 缺必选参数     → 补 params.csv
  G22 占位符过多     → 能用现网值就补
  G25 缺配套族       → 补规划行
  G27 跨网元配不了   → 写进「本网元无法配置的项」
  G29 SET 属性族漏   → 补 params.csv
  G30 RMV vs ADD     → 改动词
  G31 规划表通配     → Step 3 已处理
```

# 第四部分：需要补的算子（P0）

## 4.1 按参数依赖推导命名派生（不是字符骨架归纳）

用户纠正：
> 不是靠命名推出来的，是靠 name 这类参数依赖推出来的

### 做法

```python
def resolve_name_derivation(exp_path, family_a, family_b):
```
