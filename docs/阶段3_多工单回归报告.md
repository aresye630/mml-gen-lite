### 多工单回归后暴露的 4 个真实问题

#### 问题 1：属性族补齐（M4）在 12 单上完全空转

```
修改前：M4 真正有效 0/12 单
```

**根因**：`_find_owner_families` 只识别意图里「按现网同类XX「YY」配齐」的精确措辞。
实测 86 单中只有 19 单（22%）有这个措辞，但 **62 单（72%）的规划表里有 ADD APN/POOL/RULE 等对象族**，这些对象的属性族同样需要补齐。

**修法**：改为双路径
- 路径 1（精确）：意图说「按现网同类 X「Y」配齐」→ 参照值已知
- 路径 2（推断）：规划表里有 `ADD <对象族>` → 自动选属性最全的参照

#### 问题 2：规划表两种写法不兼容

```
写法 A（动词+族名同列）：fam_cell = "ADD APN"            ← 15/22 个规划表
写法 B（动词分列）：    fam_cell = "POOLGROUP（UDG）"
                      动作列 = "ADD"
```

旧代码只处理写法 B → 实测仅 1/20 能匹配。
修法：两种写法都识别。

#### 问题 3：`_find_owner_families` 返回 dict 但调用方按 tuple 解包

```python
for of, ref_val, target_val, intent_fams in owner_fams[:3]:   # ← dict 不能这样解包
```

**静默失败**：被 `try/except` 吞掉，Step3 返回空结果，看起来像「无 owner 族」而不是报错。

#### 问题 4：评测产物目录布局与容器不同

```
容器内：analysis_code/命令族规划.md
评测产物：直接放会话根目录
```

修法：自动探测两种布局。

## 三、结论

### 验证方法学的改变

```
之前：1 个真实工单 + 构造用例 → 161 项通过
现在：12 个真实工单（分档）+ 构造用例 → 逐单结果表
```

**关键差异**：之前不知道系统在别的工单上会不会崩，现在知道 12 单全部无崩溃，且暴露了 4 个真实 bug。

### 仍然存在的问题

1. **只有 23/86 单有规划产物** —— 63 单无法做端到端检查（评测未跑到）
2. **M4 在无产物的单上无法验证** —— 无法从规划表反推 owner 族
3. **验证仍是「模块级」不是「端到端」** —— 用已有产物 + 意图，不重跑 agent

### 下一步

- P0-8 端到端验证（等用户指示）需要重跑 agent，才能真正验证整链
- 建议端到端用 6 单（小/中/大 × 单/双网元各 1）而不是 12 单，控制时间
