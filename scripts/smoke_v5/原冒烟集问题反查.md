## 二、问题类别一：**测试太粗**（只判存在性，不判内容）

### 1.1 D4「产物完整性」只数文件在不在

**实测对比**：问题 #5.2 中，agent 路径的 `mml.txt` **存在**（19 字节，只有一行注释）。
按 D4 的判据（文件存在 + 在 produced 列表），**这条会 PASS** —— 但产物实际是空的。

```
现判据:  produced 含 mml.txt / params.csv / 确认清单.md  →  PASS
应有判据: mml.txt 非空 且 行数 > 1 且 含真实命令（非纯注释）
```

**⇒ D4 对问题 #5.2 零判别力。**

### 1.2 D1「抽样渲染」不校验渲染结果的内容

**实测**：批量路径 mml.txt 有 560 条命令，但**没有任何用例校验**：
- 引号是否成对（问题 #6）
- 参数值是否为空（`=,`）
- 命令是否可被解析

**⇒ 本次 T5 新做的"语法/引号/空值"校验，在原冒烟集里完全缺失。**

### 1.3 B1「三库齐备」只查集合非空

**实测**：三库条数正确（1504/9583/35755），但**产品分布**从未被校验。
本次 T6 才发现分布需逐个核对（发现 nav UDG=3/UNC=2 是源数据如此）。

**⇒ 原判据"集合存在且非空"无法发现"某个产品一条没导"**（历史事故：
"UDG/UNC 为什么一条没导？"正是这类问题）。

### 1.4 C3「业务问答」无质量判据

```python
def c3_business_qa():
    """业务问答"""
    # 判据（据代码）: 有输出即可（非空）
```

**实测**：T1 发现 `/api/chat` 的回复里**混入 hermes 安装日志**（问题 #10），
且回复内容称"数据集为空"（与实际不符）。**这类问题在"有输出即 PASS"下全被放过。**

## 四、问题类别三：**不关注体验**

### 3.1 无任何"文案质量"判据

实测发现的问题中，**4 个是纯体验问题**，原冒烟集全部无法覆盖：

| # | 问题 | 原判据能否发现 |
|---|---|---|
| 1 | 冗余入口（不可用按钮） | ❌ |
| 2 | 「第 N 步」内部计数外露 | ❌ |
| 3 | 完成态显示"生成中" | ❌ |
| 10 | 安装日志混入回复 | ❌ |

### 3.2 无"错误呈现质量"判据

实测问题 #4/#9：`INTERNAL` / `rc=1` 被暴露给用户。
原冒烟集**只判"失败被捕获"**，不判"提示是否对用户有意义"。

**⇒ 与用户口径冲突**（"UI 只呈现业务澄清 + 明确成败；
降级/跳过/丢参属内部逻辑不外露"）。

### 3.3 无"状态一致性"判据

问题 #8（任务 failed 但 gen 卡 producing）——
原冒烟集没有任何"跨表状态一致性"检查。

### 3.4 selftest 只验断言判别力，不验"该测的都测了"

`--selftest` 做得**很好**（16 条正/反 fixture 验证断言有判别力），
但它只回答"断言本身可信吗"，**不回答"覆盖度够不够"**。

**⇒ 断言全部可信 + 覆盖有洞 = 25/25 全绿但问题依然存在。**
这解释了为什么交付前 25/25 通过，而用户一上手就抓到 7 个问题。

## 六、根因分析：为什么会这样

### 6.1 用例设计出发点偏"资产存在性"而非"业务可用性"

原用例多为"**东西在不在**"（文件存在/集合非空/接口有响应），
而非"**东西对不对**"（内容非空/格式合法/提示可读/状态一致）。

**这是交付验收（"包装配好了吗"）的思路，不是产品验收（"能用吗"）的思路。**

### 6.2 生成路径只测了"一条腿"

D 组用例走的是**批量/装配路径**（有 rules 支撑，产物必然完整）。
**agent 路径未纳入验收** —— 而 agent 恰是交互式主路径。

### 6.3 UI 层几乎没有判据

25 条用例中 **0 条**针对 UI 呈现；UI 只有 1 个 5-step 冒烟脚本（且只走 happy path）。

### 6.4 缺"反面对照"

没有任何用例构造"应当产空/应当失败"的场景去验证系统**不静默**。

## 七、整改方向

### 7.1 判据升级（粗 → 细）

| 原判据 | 升级为 |
|---|---|
| 文件存在 | **文件非空 + 行数阈值 + 内容可解析** |
| 集合非空 | **逐产品条数 + 分布断言** |
| 接口有响应 | **响应内容质量（无内部噪音、真因可读）** |
| 任务终态 | **跨表状态一致（task vs gen）** |
| 无报错 | **不得静默：应有明确成败** |

### 7.2 补链路用例（跳过 → 覆盖）

新增：CSV 编辑链、版本链、批量三入口、下载、无 key 降级、
**agent vs 批量对照**（最关键）。

### 7.3 补体验判据（不关注 → 关注）

新增 UI 呈现检查：错误提示不含内部信号、完成态正确、
无冗余入口、无内部计数外露。

### 7.4 保持优点

- `--selftest` 的正/反 fixture 机制 **保留并扩展到新用例**
- 组内失败不中断、跑完统一汇总 **保留**
- 判别力原则 **保留**

---

## 八、结论

| 类别 | 问题数 | 典型 |
|---|---|---|
| 测试太粗 | 4 | D4 只数文件在不在；B1 只查集合非空 |
| 跳过步骤 | 7 | 无 CSV 编辑链 / 版本链 / 批量 / 下载 / 降级 / **路径对照** / UI 交互 |
| 不关注体验 | 4 | 无文案质量、错误呈现、状态一致性判据 |
| 判据错位 | 3 处漏 | D1/D4/C3 对本次问题零判别力 |

**核心结论**：
原冒烟集**"交付验收"性质强、"产品验收"性质弱** ——
它证明了"镜像装配正确"（A/E 组扎实），但**不能证明"产品可用"**（D/C 组偏浅、UI 缺失）。

本次用户一上手抓到 7 个问题，**正是这些洞的必然结果。**

**已按 7.1~7.3 的整改方向落地新冒烟集**，见 `smoke_v5/` 与 `SMOKE.md`。
