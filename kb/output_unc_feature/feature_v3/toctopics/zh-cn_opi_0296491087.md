# NRF解决方案东西向水平组网+主备容灾部署配置实例

* 操作场景
* 必备事项
* 操作步骤
* 验证方法

## 操作场景

* 对于大型运营商网络，为了便于分区域管理，可以建立不同NRF之间的东西向互联，达到全局管理的目标。

  如图1所示。

  **图1** 东西向+容灾组网举例

  在NRF分层网络中，NRF的“PRIORITY”是以**ADD NFREGNRF**，**ADD NRFBINDGRP**命令中的优先级为准（这两个命令在配置“PRIORITY”时配置一个或保持相同配置即可）。

## 必备事项

前提条件

* 各组NRF主备容灾组网的相关配置已完成，详细参考NRF解决方案可靠性配置实例（NRF主备容灾+ NF注册/更新/去注册、NF订阅/通知+NF发现）。
* 各个NRF的基础配置和NF基本功能、NF发现配置已完成，详细参考NRF解决方案基本功能配置实例的NRF侧配置。
* 主备NRF上的号段信息配置已完成，且号段信息配置一致。
* 安全相关配置已完成，访问授权和Token认证只需要在L-NRF层配置（Token分配只可能发生在目标NF注册的NRF上），TLS认证需要在所有NRF上配置，详细参考NRF解决方案安全配置实例（NRF容灾+NF访问授权&NF认证）。

数据

**表1** 配置各层NRF的相关联NRF信息

|  | TLS（TLS） | FALSE | 全网规划 | - |

|  | IP地址类型（IPADDRESSTYPE） | IPTypeV4 | 全网规划 | - |
|  | IPV4地址（IPV4ADDRESS） | * 172.16.0.7 * 172.17.0.7 * 10.10.0.7 * 10.20.0.7 | 全网规划 | 每个NRF和IP的对应关系如下：   * NRF\_Instancename\_l1\_a：172.16.0.7 * NRF\_Instancenml1\_s：172.17.0.7  * NRF\_Instance\_l2\_a：10.10.0.7 * NRF\_l2\_s：10.20.0.7 |

## 操作步骤

NRF分层组网配置

NRF单层+东西向组网的L-NRF1和L-NRF2的网络位置及规划如图2所示。

**图2** NRF的网络位置和东西向NRF组

其中，**UDM的号段路由如下：**

L-NRF1和L-NRF2上分别支持的UDM路由信息：

支持的起止号段为"123450000100000"~"123450000299999"的UDM实例组归属LGP2，

支持的起止号段为"123450000300000"~"123450000499999"的UDM实例组归属LGP1。

所以，例如L-NRF1处管辖的AMF携带号段123450000288888发起UDM请求发现时，路由顺序为：L-NRF1（L-NRF1本身和配置路由都查不到，向L-NRF2查询）→L-NRF2（L-NRF2上查询到符合条件的UDM）。

NRF侧配置

```
/*- - - - - - - - - - - - - - - - L-NRF1-A上的配置- - - - - - - - - - - - - - - - - - - - */
//一、配置NRF的基本功能数据，完成NRF作为一个基本的NF的配置。
//NRF侧路由配置已完成。

//配置NRF基础数据。
//配置运营商信息、运营商签约用户的Home PLMN。
ADD NGMNO: NOID=0, FULLNAME="Operator A", SHORTNAME="OA";
ADD NGHPLMN: NOID=0, MCC="123", MNC="03";

//打开NRF基本功能、NF发现的License。
SET LICENSESWITCH: LICITEM="LKV2NFBNR01", SWITCH=ENABLE;
SET LICENSESWITCH: LICITEM="LKV2NFDNR01", SWITCH=ENABLE;
//配置NRF实例信息，此步骤配置后系统会为NRF自动分配InstanceID信息。
ADD NFUUID: NFTYPE=NfNRF, NFINSTANCENAME="NRF_Instancename_l1_a";

//配置NRF服务化接口数据，用于跟其他NF对接交互。
//增加NRF服务化接口的IP地址。
ADD LOGICIP: IPVERSION=IPv4, LOGICIPV4="172.16.0.7", VPNINSTNAME="VRF_SBI", DESC="FOR SBI Server";
ADD LOGICIP: IPVERSION=IPv4, LOGICIPV4="172.16.0.7", VPNINSTNAME="VRF_SBI", DESC="FOR SBI Client";

//配置Nnrf接口的HTTP信息。
ADD HTTPLEGRP: INDEX=3, DESC="NRF";
//增加NRF作为服务器端的HTTP本端实体。
ADD HTTPLE: INDEX=5, HTTPLEGRPIDX=3, LETYPE=SERVER, IPTYPE=IPv4, IPV4="172.16.0.7", PORT=31000, VPNNAME="VRF_SBI", TLSFLG=NO, DESC="NRF Server";
//增加NRF作为客户器端的HTTP本端实体。
ADD HTTPLE: INDEX=6, HTTPLEGRPIDX=3, LETYPE=CLIENT, IPTYPE=IPv4, IPV4="172.16.0.7", VPNNAME="VRF_SBI", DESC="NRF Client";
ADD SBIAPLE: INDEX=3, HTTPLEGRPIDX=3, NFTYPE=NFTypeNRF, DESCRIPTION="NRF";

//二、配置NRF东西向组网。
//在NRF上配置打开NRF分层组网的License配置开关。
SET LICENSESWITCH: LICITEM="LKV2NRLNF01", SWITCH=ENABLE; 

//在L-NRF1-A上配置对应的东西向L-NRF2组信息。
ADD NRFGROUP: GROUPNAME="LGP2", GROUPATTR=SNRF;

//配置L-NRF1-A互联的主备L-NRF相关信息，为相邻且相连的NRF之间建立联系。（通过LST NFUUID查询出来INSTANCENAME）
ADD NRF: NRFINSTANCENAME="NRF_Instance_l2_a", TLS=FALSE;
ADD NRFADDR: NRFINSTANCENAME="NRF_Instance_l2_a", IPADDRESSTYPE=IPTypeV4, IPV4ADDRESS="10.10.0.7", PORT=31000;
ADD NRFPARA: NRFINSTANCENAME="NRF_Instance_l2_a", WAITINTERVAL=60, MAXRETRYTIMES=6;
ADD NRF: NRFINSTANCENAME="NRF_l2_s", TLS=FALSE;
ADD NRFADDR: NRFINSTANCENAME="NRF_l2_s", IPADDRESSTYPE=IPTypeV4, IPV4ADDRESS="10.20.0.7", PORT=31000;
ADD NRFPARA: NRFINSTANCENAME="NRF_l2_s", WAITINTERVAL=60, MAXRETRYTIMES=6;

//新增东西向LGP2组的成员L-NRF2-A和L-NRF2-S。
ADD NRFBINDGRP: NRFINSTNAME="NRF_Instance_l2_a", GROUPNAME="LGP2", ISREGED=FALSE, PRIORITY=1; 
ADD NRFBINDGRP: NRFINSTNAME="NRF_l2_s", GROUPNAME="LGP2", ISREGED=FALSE, PRIORITY=2;
```

## 验证方法

**操作场景**

该任务用于调测NRF单层组网的跨NRF的NF发现功能。

**必备事项**

* 前提条件

  操作步骤已配置完成。
* 数据

  该操作无需准备数据。
* 工具

  OM Portal跟踪

**操作步骤**

**表2** NF发现递归查询-查询归属地AUSF、UDM、PCF

|  |  |
| --- | --- |
| 测试目的 | 验证跨NRF的AMF发现SMF |
| 检查点 | 1. NF发现请求消息及发现结果消息的转发路径。 2. NRF与NRF之间，NRF和NF之间的交互消息中，信元携带符合协议要求。 |
| 调测步骤 | 1. 分别在AMF和SMF侧，执行**CLR NFCACHE**命令删除AMF、SMF上缓存的NRF发现数据（目的是为了让AMF使用NRF查询的最新数据）。 2. 执行**LST LICENSESWITCH**查询NF发现功能对应的License配置开关是否打开。    * 如果“SWITCH”为“ENABLE”，请执行3。    * 如果“SWITCH”为“DISABLE”，则执行**SET LICENSESWITCH**命令打开本特性对应的License配置开关。 3. 创建HTTP接口跟踪。 4. 构造大区间漫游用户在拜访地AMF发起初始注册，HTTP接口跟踪中观察，AMF是否向拜访地L-NRF1-A请求发现满足发现条件的归属地AUSF、UDM和PCF。    * 如果是，请执行5。    * 如果否，请执行8。 5. HTTP接口跟踪中观察，L-NRF1-A收到AMF发现请求后是否本地查询失败，L-NRF1-A向L-NRF2-A发送请求，包括： 基于routing indicator请求发现归属地AUSF；  基于supi请求发现归属地AUSF；  基于supi请求发现归属地UDM；  基于supi请求发现归属地PCF。     * 如果是，请执行6。    * 如果否，请执行8。 6. L-NRF2-A收到请求后，基于请求中的关键信息进行本地查询，得到可以目标NF的IP/FQDN，HTTP接口跟踪中观察，是否存在L-NRF2-A将查询结果回复给L-NRF1-A。    * 如果是，请执行7。    * 如果否，请执行8。 7. HTTP接口跟踪中观察，是否存在L-NRF1-A将结果返回给请求的AMF。    * 如果是，调测结束。    * 如果否，请执行8。 8. 收集信息并联系华为技术支持解决。 |

**表3** 跨NRF的订阅/通知功能

|  |  |
| --- | --- |
| 测试目的 | 验证NRF支持跨NRF的NF状态订阅，以及被订阅NF更新后触发通知的功能 |
| 背景信息 | * 订阅NF通过服务发现等手段获取到被订阅NF的nfInstanceID。 * 跨NRF的查询方式为递归查询。 |
| 检查点 | 1. 跨NRF订阅是否成功。 2. 被订阅的NF触发订阅条件的变更后，订阅通知消息的转发路径。 |
| 调测步骤 | 1. 执行**LST LICENSESWITCH**查询NF订阅对应的License配置开关是否打开。    * 如果“SWITCH”为“ENABLE”，请执行2。    * 如果“SWITCH”为“DISABLE”，则执行**SET LICENSESWITCH**命令打开本特性对应的License配置开关。 2. 创建HTTP接口跟踪。 3. NF向L-NRF1-A基于nfInstanceID订阅其他NRF上的NF的Profile Change通知请求。例如：漫游地AMF订阅归属地UDM的Profile Change请求。 4. HTTP接口跟踪中观察，是否存在AMF发送给UDM的订阅请求消息。    * 如果是，请执行6。    * 如果否，请执行5。 5. 在AMF侧，执行**LST NRFPARA**命令，检查“订阅流程开关”是否打开。    * 如果是，请执行11。    * 如果否，则执行**ADD NRFPARA**命令打开订阅流程开关。 6. HTTP接口跟踪中观察，订阅AMF发送的订阅请求消息（POST） 中是否包含订阅信息（nfStatusNotificationUri，订阅条件为nfType，事件为NF\_PROFILE\_CHANGED）。    * 如果是，请执行8。    * 如果否，请执行7。 7. 在AMF侧，执行**LST SUBCONDITION**命令查询AMF订阅UDM的订阅条件是否正确。    * 如果是，请执行11。    * 如果否，则执行**ADD SUBCONDITION**/**MOD SUBCONDITION**命令新增或修改AMF订阅UDM的订阅条件。 8. HTTP接口跟踪中观察，AMF的订阅请求是否成功。    * 如果是，请执行9。    * 如果否，请执行11。 9. 构造归属地UDM发生变更触发NRF通知。 10. HTTP接口跟踪中观察，UDM所属的NRF是否直接向订阅NF通知UDM的变更，不经过中间NRF。     * 如果是，调测结束。     * 如果否，请执行11。 11. 收集信息并联系华为技术支持解决。 |
