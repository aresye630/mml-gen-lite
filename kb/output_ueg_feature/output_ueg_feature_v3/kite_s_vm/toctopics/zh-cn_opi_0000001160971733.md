## 操作场景

N5接口位于AF（Application Function）与PCF（Policy Control Function）功能实体之间，用于传递用户应用会话请求，包括特定QoS请求、业务路由、Sponsored业务请求。

用户上线，SMF建立缺省QoS Flow后，若AF向UPCF发起业务路由请求消息，UPCF根据AF发送的用户IP进行N7与N5会话绑定，并根据应用标识和业务路由请求进行策略计算，向SMF下发指定的策略。如表1所示场景根据应用标识下发业务路由策略。

**表1** 根据应用标识下发策略

| 应用标识 | UPCF业务 | 策略控制 |
| --- | --- | --- |
| AFapp02 | AF\_RoutReq | 业务路由 |

## 对系统的影响

本特性对系统无影响。

* 操作已完成**配置UPCF与NRF的对接数据**。

| 业务Def\_Service | 此业务包括一个策略：Def\_Policy。 | 此业务用于建立N7会话，只在用户上线时触发（IPCAN\_EST）。 |
| 业务AF\_RoutReq | 此业务包括一个策略：N5\_Policy2。 | 此业务用于建立N5会话，为用户平面提供业务路由策略，仅当AF请求携带的应用标识为AFapp02时触发（AFSessionAuthorization）。 |
| 策略Def\_Policy | 此策略在用户上线时被调用，触发器为IPCAN\_EST，包含规则：   * R\_SessNorm * R\_PccNorm | 当触发器定义的事件发生时，UPCF才会进行相应的规则匹配并下发策略给SMF。 |
| 策略N5\_Policy2 | 此策略在AF请求业务路由时被调用，触发器为AFSessionAuthorization，包含规则：R\_N5Pcc2。 |  |
| 规则R\_SessNorm | * 条件：SmfSession.RatType=NR * 动作：   + Ambr（uplink=SmfSession.SubsSessAmbrUplink、downlink=SmfSession.SubsSessAmbrDownlink）   + DefaultQosInformation（5qi=9、arp=1） | 规则“类型”配置为“5G Smf Session Rule”，UPCF向SMF下发“5G Smf Pcc Rule”类型规则时一起下发，与“5G Smf Pcc Rule”动作类型中的5qi和arp保持一致，即可完成缺省QoS Flow建立。 |
| 规则R\_PccNorm | * 条件：SmfSession.RatType=NR * 动作：   + QoSData（5qi=9、arp=1）   + TrafficControlData（flowStatus=ENABLED） | 规则“类型”配置为“5G Smf Pcc Rule”。 |
| 规则R\_N5Pcc2 | * 条件：媒体类型为应用，AfSession.MediaType=Application * 动作：   + QoSData（5qi=9、defQosFlowIndication=True）   + TrafficControlData：flowStatus=AfSession.FlowStatus，还需配置路由参数routeToLocs和upPathChgEvent     - dnaiChgType=AfSession.PathChangeDnaiType     - notificationUri=AfSession.PathChangeNotificationUri     - ipv4Addr=AfSession.RouteIpv4Address     - ipv6Addr=AfSession.RouteIpv6Address     - portNumber=AfSession.RoutePort     - routeProfId=AfSession.RouteProfId | * AF侧激活的业务下动作“类型”需配置为“DynamicPccRuleIMS”。 * AF侧激活的业务下规则“类型”需配置为“5G Smf Pcc Rule for IMS”。  * 业务路由规则可以通过规则下发5qi=9、defQosFlowIndication=True，将媒体流直接绑定到默认QoS Flow。 * 业务路由规则需要TrafficControlData动作类型配置routeToLocs和upPathChgEvent，且满足配置要求：   + routeToLocs：如果动作元素配置为取值，则所有元素均需配置为取值，如果动作元素配置为源于对象，则所有元素均需配置为源于AfSession对象下属性，且需与属性一一对应配置。   + upPathChgEvent：如果动作元素配置为源于对象，则所有元素均需配置为源于AfSession对象下属性，且需与属性一一对应配置。 |

## 操作步骤

1. 登录UPCF Web UI界面。
2. 配置条件组。

   导航入口为“策略管理 > 策略 > 条件组”。

   * 当业务的使用需要设置控制条件时，需要配置条件组。若某规则不配置条件组，表示在同一业务里其他条件都匹配不上时，才触发此规则。
   * 条件组是一个或多个条件的组合。条件组中的各条件之间可以是“与”的关系，也可以是“或”的关系。条件之间的与/或关系由参数“关系”的取值决定。

   需要配置2个条件组，分别用于用户上线和使用应用的媒体类型。条件组的数据规划如表3所示。

   **表3** 条件组

   | 类别 | 参数 |  | 取值样例 |

   | 条件组1 | 基本信息 | 名称 | Def\_CG |
   |  |  | 关系 | AND |
   |  | 条件 | 名称 | Def\_C |
   |  |  | 对象属性 | * 对象：SmfSession * 属性：RatType |
   |  |  | 操作符 | Equal |
   |  |  | 右值类型 | Value |
   |  |  | 右值 | NR  说明：  “NR”：表示用户从5G网络接入。 |
   | 条件组2 | 基本信息 | 名称 | AFApp\_CG |
   |  |  | 关系 | AND |
   |  | 条件 | 名称 | AFApp\_C |

   |  |  | 右值类型 | Value |
   |  |  | 右值 | Application  说明：  表示媒体类型为应用。 |
3. 配置5G动作组。

   导航入口为“策略管理 > 策略 > 5G动作组”。

   此场景需配置5G动作：Ambr、Arp、DefaultQosInformation、SessionRuleAction、FlowDescription、FlowInformation、QoSData、TrafficControlData、RouteToLocation、UpPathChgEvent、RouteInformation、DynamicPccRule和DynamicPccRuleIMS。其中：

   * PCC规则类型动作：
     + DynamicPccRule：用于默认QoS Flow的建立。
     + DynamicPccRuleIMS：用于AF请求场景需要配置此动作。
   * 业务路由相关动作：
     + RouteInformation：业务路由的信息
     + RouteToLocation：业务路由的策略方法
     + UpPathChgEvent：AF订阅的用户面路径管理事件通知
   * AF请求保障带宽相关动作：
     + QoSData：当需要进行带宽控制时均需配置此动作，若不配置则表示不限制Qos。
     + TrafficControlData：当需要做门限控制时，配置此动作。在下发流描述时，如果不配默认为放通该流，当需要限制流时，此动作必须配置。此场景根据AF请求的FlowStatus，下发门限策略。

8. 登录“UPCF 业务管理”窗口。
9. 发放业务。
   1. 执行**ADD PSUB**增加一个用户。

      “USRIDENTIFIER”的参数类型受软参VRM\_SUBSRCIPTIONIDTYPE（系统支持的用户类型）控制，默认为“IMSI”。

      ```
      ADD PSUB: USRIDENTIFIER="46010381012****", USRMSISDN="1234567****", USRSTATE=Normal, USRPAIDTYPE=NULL, USRSTATION=Master, USRCONTACTMETHOD=SMS, USRBILLCYCLEDATE=NULL, USRSUBNETTYPE=eMBB-SA;
      ```
   2. 执行**ADD PSRV**给用户签约业务。

      ```
      ADD PSRV: USRIDENTIFIER="46010381012****", SRVNAME="Def_Service", SRVUSAGESTATE=Normal, SRVROAMINGTYPE=NULL;
      ```
